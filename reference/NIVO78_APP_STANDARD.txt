## CURSOR ENFORCEMENT ARCHITECTURE (MANDATORY)

This standard is the policy source of truth. Cursor must NOT be given this entire document as one monolithic always-on rule. The repository MUST project the standard into focused `.cursor/rules/*.mdc` files.

### Rule architecture
- `nivo78-core.mdc` — **[ALWAYS APPLY]** compact router, non-waivable principles, precedence, deviation/override policy, and required agent workflow.
- Focused `.mdc` files — **[APPLY INTELLIGENTLY]** by concern: product philosophy, UI/input, architecture/data, security/vault, feedback/support, legal/privacy, accessibility/I18N, recovery/upgrades, testing, release/supply chain, web/marketing, and performance.
- Release verification rules may be manually invoked for final certification; they must never be treated as satisfied merely because the agent says they passed.
- Each focused rule file MUST remain below 500 lines. If it grows beyond that, split it by concern rather than weakening or omitting rules.

### Rule-file contract
Every `.mdc` rule MUST have YAML frontmatter containing `description` and an explicit `alwaysApply` value. File names MUST be stable and descriptive. Rules MUST use imperative, testable language: **MUST**, **MUST NOT**, **SHOULD**, or **MAY**. Avoid vague phrases such as “try to” or “generally.”

### Source-of-truth contract
- Edit the canonical standard and rule-ID catalog first.
- Cursor projections are maintained from the canonical source and registry; do not treat projections as independent policy. Validate their metadata and globs after standards changes.
- Every projected rule MUST preserve its canonical rule IDs.
- No Cursor rule may silently create a new product requirement that is absent from the canonical standard.

### Agent workflow
1. Identify the product surface being changed: app, shared engine, web, legal/support, release tooling, or multiple surfaces.
2. Apply `nivo78-core.mdc` plus every focused rule whose description matches the work.
3. Before editing, identify applicable rule IDs and their enforcement class: `[STATIC]`, `[GATE]`, or `[QA]`.
4. Implement the smallest change that satisfies the applicable rules.
5. Run the applicable automated verification. For `[QA]`, perform or document the required human/audit check.
6. Do not claim compliance from inspection alone when a `[GATE]` script/test is required.
7. If a rule cannot be satisfied, STOP and use the documented standard-override process. Never disable a verifier globally to make a violation disappear.

### Precedence
1. Never-waivable Nivo78 controls.
2. Applicable canonical Nivo78 rule.
3. Product-specific implementation detail that does not conflict with the standard.
4. Accepted, current product override with owner, reason, risk, compensating control where applicable, and review trigger/date.

If two applicable Nivo78 rules appear to conflict, do not choose silently. Surface the conflict and resolve it in the canonical standard or through the approved override mechanism.

### Cursor limitation
Cursor rules are AI guidance, not a security boundary. Mandatory `[GATE]` requirements MUST have executable verification outside the model’s judgment. Cursor documentation likewise recommends focused rules, clear descriptions, and keeping rules under 500 lines.

[STATIC] Enforced by Cursor always-on rules or
standard linters (IDE).

[GATE]  
Enforced by automated verify / release-gate scripts (build).

[QA]    
Verified by human review or documented SOP (audit).



Never waivable (do not override):

  [GATE] Silent
upload of business data

  [GATE] Silent
diagnostics / background bug reporting

  [GATE]
Breadcrumb logger or attachBreadcrumbsToBugReport in release / main

  [GATE]
Intentional security bypasses in release (debug unlocks, test credentials,
development endpoints)

  [QA]   Pre-checked legal acceptance

  [STATIC] Vault
/ secrets bypass (plaintext secrets after save, support reset of master
password)

WHAT CONSTITUTES A GOOD NIVO78 APP



Through-line

\- Utility first. Your data under your control. Never
pay for fluff.

\- Brand stamp (public + in-product voice): Local-First
Software. The way we think apps should be.

  Do the job.
Respect the user. Skip the fluff. Cloud is optional, never required.



Brand Philosophy (keep every app Nivo78-like)

\- Mission: Build professional-quality software that
respects its users.

\- Public home: https\://nivo78.com/about/ (Website
include/n78\_company\_philosophy.php) — product

 
About/Help/support copy must not contradict this philosophy.

\- Guiding test: Would a user feel the software exists
to help them accomplish their goals —

  not to
monetize their attention, harvest their data, or lock them into an ecosystem?

\- Trust test (copy and product): After reading the
product page and Help, would a careful customer

  still be
surprised by a hard limit, missing automation, or handoff they must do
themselves?

  If yes, the
copy failed — fix the claim, not the customer’s expectations.

\- Core principles (every product MUST honor unless an
accepted standard override records otherwise):

  - Local-First
— working data stays on the device; everyday use does not require the Internet.

  - Cloud
Optional — cloud may add value; cloud is optional, never required for core
work.

  - No Account
Required — start immediately; no mandatory Nivo78 sign-up for daily use unless

    the
product’s explicit job requires an account (document that exception).

  - No In-App
Advertising — no banners, pop-ups, or sponsored content.

  - No User
Tracking — no behavioral tracking, no selling user data, no advertising
profiles.

  - Strong Data
Security — encrypt secrets appropriately; data leaves the device only when the
user chooses.

  - Your Data Is
Yours — export anytime; open formats when practical; no vendor lock-in.

  - Fair
Business Model — clear product pricing—one-time purchase or subscription—where
each

    product
provides real value; no tolls on using the app without valid maintenance,
development,

    or
infrastructure costs. This is one of the ways we keep your costs low;
subscriptions are fair

    when they
fund ongoing support, updates, or services — not as a toll on finished offline
work

    that does
not need our servers; low cost — focused apps, honest tiers, no fluff markup.

  - Fast &
Reliable — starts quickly on the device; responsive UI; works offline and
during outages / remote use.

  - Respectful —
no nag screens, notification spam, constant review requests, or manipulative
design.

  - Transparent
— honest privacy policy, clear pricing, and plain talk about what the product
does

    and does not
do; no hidden surprises after install or purchase.

  - Built to
Last — remain useful for years; data stays accessible if cloud services are
unavailable.

\- Brand statements (use on hub, About, store/marketing
where accurate):

  - Software
that works for you—not on you.

  - Tools you
run. Data you control.

  - Professional
apps built around users, not business models.

  - Cloud is
optional, never required.

  - The way apps
should be.

  - Do the job.
Respect the user. Skip the fluff.

  - Local-first.
Low cost. Your data belongs to you.

  - Honest about
what we do — and what we don’t.

\- Deliberately avoid (in addition to the won’t-do list
below): forced account creation; required host

  login for core
offline work; excessive permissions; Internet required just to open the app;

  tolls on using
the app without valid maintenance, development, or infrastructure costs (this
is

  one of the
ways we keep your costs low); proprietary-only data formats; manipulative
feature

  locks;
manipulative microtransactions; hidden pricing;

  unnecessary
background activity; marketing or Help that oversells automation, sync, or

  the shipped
build does not deliver.



One job, done well

\- The app solves one clear problem — not an
“everything platform.”

\- A user can finish the core workflow without
memorizing external manuals.

\- The app prepares and validates work, then hands off
when needed — it does not pretend to replace the user’s primary external tool
(browser, email client, accounting site, file host, etc.) unless that
replacement is explicitly shipped and labeled.



Utility-first UI

\- Compact, scannable layout — easy to read at a
glance, not decorative.

\- Visible controls only: buttons, checkboxes, menus,
tabs — no hidden gestures as primary actions.

\- Plain language on every screen users see — labels,
errors, help, and empty states.

\- Non-trivial fields get ? help; dangerous or
irreversible warnings stay inline.

\- Form state preserved when navigating back until the
user saves or dismisses.



Local-first and trustworthy data

\- Core workflows work fully offline.

\- The user’s working data stays on the device by
default.

\- Cloud login, sync, and backup are optional when offered
— never required for daily work.

\- No Nivo78 account required for daily use unless the
product’s job explicitly needs it.

\- No nags, behavioral profiling, telemetry for resale,
or silent “phone home” analytics.

\- Secrets encrypted at rest; after save, secrets are
copy-only and not shown on screen again.

\- Sensitive identifiers blocked from plain saves when
product policy requires a vault.

\- Clipboard cleared after a short timeout when the
platform supports it.



Clean architecture (multiplatform products)

\- Business rules, validation, persistence, export, and
vault live in shared engine code — not scattered in UI except trivial view
state.

\- No platform-specific APIs in shared engine code; OS
access goes through bridges or injected abstractions.

\- Paths and storage semantics are neutral in engine
code — no hardcoded OS jargon in shared logic.

\- Android, iOS, and desktop behave consistently
because they share one rules engine.

\- Debug-only 10,000-event breadcrumb ring buffer lives
in shared engine code (expect/actual

  isDebugBuild +
MutexLock). UI intercepts touch, navigation, and field length — never raw text.



Workflow quality

\- Collect shared facts once (profile, organization,
defaults) and reuse — do not re-ask the same data on every screen.

\- Ask for context-specific details only where that
context truly differs (e.g. separate external accounts or listing contacts when
the product supports multiple destinations).

\- Validate before save using published rules — not
only at export time.

\- Checklist or status indicators match engine truth
(not started / needs attention / complete).

\- Empty, loading, and error states on major screens —
not happy-path only.



Handoff honesty

\- The app says plainly what it does vs what the user
must do in an external app, site, or service.

\- Network use is user-initiated and labeled (open
browser, send email, confirm purchase) — never silent transmission of user
data.

\- No implied automation the product does not perform
(upload, charge, sync, “we’ll submit this for you”) unless that capability is
actually shipped.

\- Readiness is obvious: what is done, what is missing,
what to do next.



Expectation honesty (no negative customer surprises)

\- Trust is built by stating features and limitations
in the same breath — on the product webpage,

  in Help, in
About/upgrade copy, and at the step where a limit matters.

\- Prefer “does X; does not do Y” over glowing
capability claims that omit the boundary.

\- Limits that change outcomes (tiers, offline vs
online, handoff vs automation, platform gaps,

  what stays
on-device vs what the user must do elsewhere) MUST be discoverable before the
user

  depends on the
wrong assumption — not only after a failed action.

\- Help articles for non-trivial tasks MUST include
rules and limits, not only happy-path steps.

\- Website “will do / won’t do” sections, store listing
claims, and in-app Help MUST agree with

  shipped
behavior in the current build — overselling is a defect, same as a wrong
calculation.

\- When scope is preparation-only, say so. When a
calendar, store portal, bank, or mail app still

  has the last
step, say so. When a setting or feature lives on one surface only (e.g.
calendar,

  not Settings),
say so.



Help and support

\- Searchable Help hub: browse, search, deep-link by
article id where the product uses that pattern.

\- Structured Feedback (report type, contact,
narrative, optional diagnostics); user reviews before send.

\- Menu or equivalent includes Help, Feedback, Support,
Privacy, and Terms (or documented equivalent placement).

\- Help and support copy encourage trust: accurate
capabilities, clear limits, plain next steps —

  never
marketing that sets up disappointment after install.



Commercial honesty

\- Free tiers are genuinely useful — not demo timers or
crippled core jobs.

\- Paid upgrades add caps or extras — not tolls on
finished work the user already created.

\- No tolls on using the app without valid maintenance,
development, or infrastructure costs. This is one of the ways we keep your
costs low.

\- Subscriptions are fair when they fund ongoing
support, updates, or services — not as a toll

  on finished
offline work that does not need our servers.

\- Keep prices as low as practical utility allows —
focused scope, no fluff markup.

\- Customer-facing copy matches shipped behavior in the
current build.

\- No “coming soon,” “planned,” or roadmap language
unless the feature is declared shipped for this version.

\- Copy is complete: users can discover what the app
does, what it does not do, limits, handoffs, and platform restrictions (Help, privacy,
about, upgrade, or critical inline warnings).

\- Product web pages publish explicit “what it will do
for you” and “what it won’t do for you” sections derived from this standard and
the product’s MARKETING\_COPY.txt — not buried in a single paragraph.

\- Every public product web page includes comprehensive
SEO metadata in the same pass as copy edits: unique title, meta description
(\~160 characters), canonical URL, Open Graph, and Twitter cards — verified by
the product website script (WEB SEO checks).



Technical bar for a good Nivo78 app (engineering — not
customer marketing)

\- Shared outlined fields on critical paths; engine
validation; Enter/IME and blur commit (APP-INPUT-COMMIT).

\- Required format/validate on blur / Done / leave /
Save only (APP-INPUT-FORMAT-ON-COMMIT).

\- Flush blur-only drafts before same-screen persist
(Save / Lock / Next / Finish) and before

  page-leave
persist — a control that does not steal focus still writes what is on screen

 
(APP-INPUT-FLUSH-BEFORE-PERSIST). Persist from the inner field commit
(the text just typed).

  Do not persist

INPUT STANDARDIZATION — SAME INPUT STYLE IN EVERY APP

\================================================================================



Field components (mandatory for form rows)

\- Single-line text, multi-line text, email, phone,
URL, and numeric fields use the shared outlined field component — same border,
label placement, focus ring, and error line placement.

\- Typed fields (email, URL, phone, postal, clock
times, money/duration with unit, application IDs) use shared input profiles
where the product has them: validation messages from engine rules — not ad hoc
regex in Composables.

\- Password and secret fields use the vault pattern:
masked entry, save once, copy-only after save — never re-display plaintext secrets.

\- Dropdowns and filter chips for small fixed sets;
free-text only when the value is truly open-ended.



Format and validate on commit (mandatory — not while
typing; internal engineering — not marketing)

\- Required format and validation for structured fields
run only on blur, IME Done / Enter commit, leave, or Save — never on every
keystroke.

\- Canonical rewrite (pad minutes, insert separators,
snap to \`h\:mm AM/PM\`, phone mask completion, URL scheme fill, etc.) happens at
those commit points only.

\- While focused, leave the draft as typed. Do not
fight mid-edit by rewriting partial values or jumping the cursor to the end
after each character.

\- Light mid-edit filters are allowed when they do not
change structure or fight the caret: digit-only filters, paste-noise strip,
case of AM/PM letters, keeping a live draft for dirty/required UI when storage
commits on blur.

\- Format errors stay under the field (and on the save
bar when the page has one) after commit failure — not as a live “invalid” flash
while the user is still typing a partial value.

\- Do not put this rule in customer-facing will/won’t,
Brand Philosophy, About, store, or Help marketing copy — it is build/QA
guidance (APP-INPUT-FORMAT-ON-COMMIT; pairs with APP-INPUT-COMMIT).



Flush blur-only drafts before persist (mandatory —
APP-INPUT-FLUSH-BEFORE-PERSIST)

\- When storage commits on blur / Done only, parent
state can still hold the previous value while

  the focused
field shows a newer draft.

\- Save, Lock, Next, Finish, customer handoff, and
page-leave autosave MUST flush registered

  field drafts
first (\`commitAll\` or the product’s equivalent), then persist. A control that

  does not steal
focus is still required to persist what is on screen.

\- The persist MUST use the inner field’s committed
text. MUST NOT register a second persist that

  reads a
leftover parent copy (previous \`localValue\` / \`rememberUpdatedState\`) and runs
before

  the inner
field flushes — that writes the old minutes/rate/name.

\- Flush order: innermost field state first, then parent
persist callbacks.

\- After flush, Lock/Save MUST assemble from live
editor fields (current line items, duration,

  settings), not
a \`remember {}\` derived snapshot from the last composition.

\- IME Done / Enter remains a commit path; it is not a
substitute for flushing on Lock/Save.

\- Guardrail tests MUST cover every host of a blur-only
outlined duration/money/clock/settings

  row (or an
equivalent structural scan), not only one screen.

\- Customer-facing will/won’t uses the plain language
above (persist what is on screen). Do not put

  \`commitAll\`,
commit registry, or blur jargon in Brand Philosophy, About, store, or Help
marketing.



Focus behavior (mandatory — all input fields; internal
engineering — not marketing)

\- When a text field receives focus, place the caret
for in-place edit (tap position or platform default). Do nothing else to the
value.

\- MUST NOT select-all on focus (including “select all
when not blank”).

\- MUST NOT clear or erase the field on focus.

\- Replace-all remains user-initiated (platform Select
all / Ctrl+A / Cmd+A / long-press), never automatic on focus.

\- Applies to profile, settings, quotes, search, and
every other outlined or shared text input — same rule family-wide.

\- Rule id: APP-INPUT-FOCUS-EDIT-ONLY. Not
customer-facing will/won’t or Brand Philosophy copy.



Field row layout

\- Label on the primary form row; ? help icon aligned
to the label when the field is non-trivial.

\- Validation errors appear directly under the field in
plain language; engine message wins over UI paraphrase.

\- Required vs optional is explicit in the label or
helper line — never implied only by validation failure on save.

\- Placeholders supplement the label; they do not
replace it.



Commit and keyboard behavior

\- Enter / IME Done commits the field and moves focus
predictably (or triggers save when that is the established pattern for inline
rows).

\- Blur commits draft text to view model state; dirty
tracking reflects engine comparison — not string equality in the Composable
alone.

\- Same-screen persist (Save / Lock / Next / Finish)
and page-leave MUST flush those drafts even when the control does not steal
focus (APP-INPUT-FLUSH-BEFORE-PERSIST).

\- Commit is also when required formatting and field
validation run (see Format and validate on commit above).

\- Focus does not select-all or clear (see Focus
behavior above).

\- Long text areas cap length with visible feedback
before send/save fails silently.



Save and cancel semantics (same everywhere)

\- Save validates through engine coordinators first; UI
shows the first blocking message.

\- Cancel on a dirty form reloads from disk or reverts
draft — same wording (“Cancel changes” / “Discard”) per platform shell.

\- Save bar: primary Save, secondary Cancel, optional
status line for last save or error — pinned bottom on mobile, consistent strip
on desktop. When Save fails engine validation, every message appears in error
styling immediately above the save bar (not only at the top of a long page).
Back and Cancel on that page are disabled until validation clears or the user
chooses Save anyway where acknowledgement warnings apply (APP-SAVE-BAR).

\- Save stays inactive when the draft matches last
registry-verified values; enable when dirty;

  after write,
stay active until read-back matches, then inactive (APP-SAVE-VERIFIED-INACTIVE).

  Failed write
keeps Save active and uses Could not save — not a success toast.

\- Home / Back with a typed Save draft
(APP-LEAVE-DIRTY-PROMPT): flush; persist when valid;

  block leave
when invalid or save fails. Save = save now and stay. Hint: Valid changes save

  when you
leave. Optional Save / Don't save / Stay dialog only with accepted override.

  Toggles /
checkboxes / frequency chips MAY persist immediately.



Pickers and file input

\- File and folder pickers go through platform bridges;
engine receives neutral paths (okio.Path or equivalent).

\- After pick: show filename or path summary in the
same read-only row pattern; user can replace, never edit path as raw text
unless the product explicitly supports path entry.

VAULT AND MASTER-PASSWORD CONTRACT — EVERY APP

\================================================================================



Principle

\- Secrets and vault behavior are identical in promise
across Nivo78 apps: encrypt at rest, copy-only after save, user holds the keys.



Master password and recovery

\- Master password (or product-equivalent vault key) is
never stored in plain project files or transmitted to Nivo78.

\- When a product uses a master password, it MUST
generate a high-entropy one-time recovery key at first set

  (APA pattern:
grouped unambiguous characters). Show it once with a critical warning: store it
off the device,

  not in the
same place as the master password; Nivo78 never receives it; there is no
email/phone/support reset.

\- The recovery key MUST let the user set a new master
password. It MUST NOT reveal the old password.

 
Password-protected files already sealed with the old password stay tied
to that password unless the product

  also wraps
those files with a data key (document that limit honestly).

\- Using the recovery key MUST issue a new recovery key
and invalidate the old one. Confirm the user saved the

  new key before
the reveal dialog can close.

\- Existing installs that already have a master
password MUST issue a recovery key the next time the user

  enters that
password — never from biometric unlock alone, and never from an unlocked phone
with no secret.

\- Recovery key / recovery mechanism loss is warned
inline — critical, plain language: if both the master

  password and
the recovery key are lost, encrypted secrets and old password-protected files
cannot be recovered.

\- Failed unlock shows honest message — no hint that
reveals secrets; optional retry without leaking vault contents.



Secret entry and display

\- Masked entry for passwords and tokens; save once
through engine coordinator.

\- After save: copy-only access — value not shown on
screen again; replace/remove flows use confirmation when policy requires.

\- Sensitive identifiers (bank, routing, IBAN, payout
IDs) blocked from plain JSON saves where product policy requires vault.



Vault lock and scope

\- Vault lock timeout behavior documented in Help or
security copy when product auto-locks.

\- Unlock scope honest: what requires master password
vs what remains readable plain text in project folders.

\- Clipboard copy of secrets auto-clears after short
timeout when platform supports it; user sees one-line notice.



Order relative to legal gate

\- Document and keep consistent: first-run Terms

\- Backup artifact named clearly (product, context,
date/version).



Restore

\- Restore path documented in Help; user selects file;
confirm before overwrite when existing data would be replaced.

\- Restore failure reports honestly — partial restore
rolled back where policy requires; no false success.



Leave and uninstall

\- Privacy policy and Help state what remains on disk
after uninstall vs what the app removes.

\- User can export or backup before destructive remove
flows — discoverable from settings or data security area.

\- No vendor lock-in: core working data exportable in
open or documented formats (JSON, CSV, PDF, encrypted bundle, etc.)

  without
requiring the app shell or a proprietary service to parse it
(APP-DATA-OPEN-EXPORT, APP-DATA-PORTABILITY).



Process restore (APP-LIFECYCLE-STATE-RESTORE)

\- Engine persists active workflow state continuously.

\- If the OS kills the process while backgrounded, the
next cold start resumes the exact screen and draft state —

  not a false
empty workspace.





\================================================================================

SCHEMA VERSION AND MIGRATION — EVERY APP

\================================================================================



Principle

\- Persisted data carries schema version; engine
migrates forward or fails closed — UI never pretends empty when load failed.



Versioning rules

\- Every persisted JSON, vault file, and backup format
declares schema version in engine — single source of truth.

\- Load path: detect version → migrate in engine when
supported → or block with plain message when not.

\- Migration logic lives in engine packages — not in
Composables.



Fail closed

\- Corrupt or unreadable session file: show
operator-facing error — do not silently reset to blank workspace that looks
saved.

\- Partial save failure: report which parts failed; do
not mark all clean when engine reports partial failure.

\- Reload from disk after Cancel uses same engine load
path — same failure semantics as cold start.



Testing

\- Engine tests cover migration from prior schema
version and corrupt-file handling on critical stores
(APP-DATA-SCHEMA-MIGRATION).

\- Pair with Error detection and recovery.txt and Data
integrity.txt text tests when changing persistence.

APP-A11Y-WCAG-FLOOR [QA]

APP-A11Y-KEYBOARD [QA]

\- Desktop interfaces must support logical keyboard

without requiring a pointer.



APP-A11Y-NO-COLOR-ONLY [QA]

\- Do not communicate required information, errors,
status, or actions through color alone.



APP-A11Y-TEXT-SCALING [QA]

\- Display Resolution Awareness & Full UI Scalability: Every application MUST be
display resolution aware and render sharply and correctly on high-resolution (HiDPI / 4K / Retina)
displays. Large text, system text scaling, display zoom percentage changes (100%, 125%, 150%, 175%,
200%, 250%, 300%+), and dynamic per-monitor DPI transitions must scale the entire application appropriately.

\- High-DPI Startup Contract: On desktop platforms, high-DPI awareness (e.g. PerMonitorV2) must be
explicitly declared at startup prior to any UI font or control creation, preventing low-DPI bitmap
blurriness and scaling distortion.

\- Critical controls, inputs, numeric spinners, dropdowns, buttons, sliders/trackbars, labels,
validation messages, and navigation must remain fully visible, readable, and operable without
text truncation, squashed heights, or clipping.

\- Fixed 96-DPI pixel heights and widths on interactive chrome are prohibited. Input heights and
bounds must adapt dynamically to font metrics and DPI scale factors (e.g. using preferred heights
or DPI-scaled dimensions).

\- Vector Glyphs & Assets: Render UI icons, history arrows, and visual markers as vector paths
or multi-density assets scaled to the active DPI rather than fixed unscaled raster bitmaps.

\- Grouped controls (such as a label, slider groove, and value readout) must be encapsulated to
wrap and move together as atomic units rather than fragmenting across line breaks.

\- Dialogs, help hubs, and legal gates must support dynamic font/DPI auto-scaling.



APP-UI-UNIFORM-SURFACE-VIEWPORT [GATE]

\- Applies to Nivo78 desktop workstation applications with dense fixed-layout surfaces
(worksheets, grids, takeoff, quoting). Complements APP-A11Y-TEXT-SCALING; mobile fluid
layouts and approved product overrides (documented WinForms exceptions) are out of scope.

\- Canonical logical design surface: BaseWidth 1920 × BaseHeight 1080 at 100%. Scaled
surface dimensions = base × ScaleFactor where ScaleFactor = deviceDpi / 96 (single global
scale for layout — one ScaleLogical / ScalePx path; WinForms AutoScaleMode.None on main shell).

\- One primary main viewport per top-level window onto the scaled surface. Use explicit
horizontal and vertical scrollbars with manual content offset (family reference:
CompactMainViewportHost in N78-Estimate). Do NOT use ScrollableControl.AutoScroll as the
primary host for the full application surface (AutoScroll drift causes left/top gutters at scroll home).

\- Scroll home: when scrollbars are at minimum, origin (0,0) of the scaled surface MUST align
flush with the viewport top-left (no large empty margin). Mouse wheel handling MUST parse
WM_MOUSEWHEEL delta as signed 16-bit (no Option Strict overflow on unsigned high word).

\- Pane layout: inner split/worksheet hosts MUST NOT size to the full scaled canvas width
inside a narrow pane in ways that clip totals; outer main viewport owns horizontal pan.
Nested hosts in compact mode MUST NOT compete with duplicate horizontal AutoScroll.

\- New desktop-dense products MUST port AppUiScaling + CompactMainViewportHost (or shared
extract) per N78Kit — do not invent a one-off DPI or scroll scheme.

\- Canonical spec: reference/NIVO78_UNIFORM_UI_SURFACE_AND_VIEWPORT.md. GATE evidence:
acceptance checklist in that document plus product guardrail/unit tests where applicable.

APP-DATA-DOCUMENTS-ROOT [GATE]

- Desktop applications MUST store all user data, databases, business profiles, price books, templates, job libraries, blueprints, session settings, and exports under a dedicated, user-visible folder in the user's standard Documents directory (e.g. `Documents\N78-<AppName>\`), never hidden inside `AppData`, `LocalApplicationData`, `Roaming`, or hidden dot-directories.

Placing persistent application data or settings in `AppData` creates an unacceptable risk of silent data loss during system resets or PC migrations.

- Sibling desktop apps MUST include automatic migration on startup from legacy `AppData` locations into the `Documents` directory without data loss or user friction.

consistent snapshot.

to detect corruption or unauthorized modification

  before
restore.

  modifying
current application data.



APP-RESTORE-NO-DATA-LOSS [GATE]
